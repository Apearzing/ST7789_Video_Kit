# 通信协议：PC → STM32 帧格式与流控

> 一份简单的、够用的、十年不用改的自定义协议。设计目标是：**开销小、能自恢复、对位深和分辨率完全透明**。

---

## 1. 设计取舍

| 需求 | 做法 | 为什么不用别的 |
|---|---|---|
| 定界 | 2 字节魔数 `55 AA` | 用长度字段定界的话，一旦丢一个字节就永久错位；魔数能靠"重新扫描"自恢复 |
| 完整性 | 16 位字节累加和 | CRC16 更严谨，但 6400 字节累加和已经够抓线材干扰；累加和算得比 CRC 快一个数量级 |
| 流控 | ACK / NACK 单字节 | 不需要滑动窗口——1.5 Mbps 下 RTT 只有几十微秒，停等协议就够了 |
| 分辨率透明 | W/H 在帧头里 | 上位机改分辨率不用改固件 |
| 位深透明 | **用 LEN 反推** | 见 §4，这是最省事的设计 |
| 字节序 | 小端 | 与 x86/ARM 一致，两边都直接 `struct.pack("<")` |

## 2. 帧结构

```
┌────────┬────────┬────────┬────────┬──────────────┬──────────┐
│ 0x55   │ 0xAA   │  W     │  H     │   LEN        │  DATA    │ CHECKSUM │
│ magic  │ magic  │ u16 LE │ u16 LE │   u32 LE     │ LEN 字节 │  u16 LE  │
└────────┴────────┴────────┴────────┴──────────────┴──────────┘
  1 B      1 B      2 B      2 B      4 B            0~28.8 KB    2 B
```

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | magic0 | 固定 `0x55` |
| 1 | 1 | magic1 | 固定 `0xAA` |
| 2 | 2 | W | 帧宽，1~120 |
| 4 | 2 | H | 帧高，1~120 |
| 6 | 4 | LEN | 数据长度，必须是 `W*H`（8 位）或 `W*H*2`（16 位） |
| 10 | LEN | DATA | 像素数据，**行优先，每行从大到小排列** |
| 10+LEN | 2 | CHECKSUM | `sum(DATA) & 0xFFFF`，**不含帧头** |

**像素数据排布**：

- 8 位（RGB332）：每像素 1 字节，`R[7:5] G[4:2] B[1:0]`
- 16 位（RGB565）：每像素 2 字节，**高字节在前**（big-endian），`RRRRRGGG GGGBBBBB`

> 注意这里有个容易踩的坑：**帧头是小端，像素数据是大端**。因为屏要的是"高字节先发"，而上位机的 `numpy.astype('>u2')` 恰好能给大端字节流，直接透传最省一次转换。

一帧 80×80 的 8 位帧，实际字节数 = 2 + 2 + 2 + 4 + 6400 + 2 = **6412 B**，协议开销 12 B，占 0.19%。

## 3. 握手时序

### 3.1 正常流程（ACK 模式）

```
   PC                                   STM32
    │                                     │
    │───── 55 AA | 80 00 50 00 | ... ────►│  收帧头，校验参数
    │                                     │  启动 DMA 收 6400 B
    │                                     │  （同时把上一帧刷到屏上）
    │───── DATA (6400 B) ────────────────►│
    │───── CHECKSUM (2 B) ───────────────►│  比对校验和
    │◄──────────────────────────── 0x06 ──│  ACK
    │                                     │
    │  收到 ACK → 立刻发下一帧              │  交换缓冲，下一轮刷这帧
```

**关键**：ACK 是在**校验通过后立刻发**的，不等刷屏完成。刷屏发生在下一轮循环的开头，与下一帧的接收并行。如果等刷屏完再 ACK，帧率会掉一半。

### 3.2 重传

```
   PC                                   STM32
    │───── 帧 N ─────────────────────────►│  校验错
    │◄──────────────────────────── 0x15 ──│  NACK
    │───── 帧 N（重发，最多 4 次）────────►│
```

NACK 触发条件只有两个：

1. 帧头参数非法（`W==0`、`W>120`、`LEN` 与 `W*H` 不匹配）
2. 校验和不匹配

**注意：参数非法时 STM32 不会去收 DATA**，直接 NACK 然后回到扫魔数状态。所以上位机重发时要从帧头开始重发整帧。

### 3.3 超时与降级

| 侧 | 超时 | 行为 |
|---|---|---|
| STM32 等帧头 | 500 ms（非首帧）/ 3 s（首帧） | 放弃本帧，回扫魔数 |
| STM32 等数据 | 2500 ms | `HAL_UART_Abort`，回扫魔数 |
| STM32 等校验和 | 500 ms | 同上 |
| STM32 等流（`V_WaitMagic`） | 1500 ms | 判定"流暂停"，把未显示的帧刷上去 |
| PC 等 ACK | 3 s | 重发；**连续 3 帧超时 → 自动切单向模式** |

**自动降级的逻辑**（上位机）：

```python
if r is None:                    # 超时
    fails += 1
    if fails >= 3:
        use_ack = False          # 转单向
        print("连续3帧无ACK，自动切换单向模式（请检查RXD-PA9回线）")
```

这个设计的意义：**接线上少一根线（RX）也能跑**。很多人第一次接线只接了 TX 和 GND，如果没有自动降级，看到的就是"一直超时 + 画面不动"，会以为代码有问题。

### 3.4 单向模式

只发不等，用固定节拍控制速率：

```python
if auto_pace:
    time.sleep(max(len(pkt) * 10.0 / baud, 0.06) + 0.005)
```

`len(pkt) * 10 / baud` 是这一帧在线上占用的时间（10 = 1 起始位 + 8 数据 + 1 停止位）。

`0.06`（60 ms）这个下限很关键：它对齐了固件刷一帧的时间（51 ms）+ 一点余量。**不设下限的话，小分辨率下上位机会发得比固件刷得快，数据在串口缓冲里堆积，延迟越滚越大**——表现是"画面延迟 10 秒"，比掉帧难受得多。

## 4. 位深自适应（协议里最巧的一处）

固件不关心上位机发的是 8 位还是 16 位，只看长度：

```c
uint32_t px = (uint32_t)w * h;
if (len != px && len != px * 2) { V_TxByte(V_NACK); continue; }   /* 校验 */
...
fbpp = (len == px) ? 1 : 2;        /* 8 位 or 16 位 */
```

带来的好处：

- 上位机切色彩模式**不用重烧固件**
- 后来加 8 位色功能时，固件只改了 3 行（`bpp` 参数 + 展开分支）
- 协议版本号都不用加——长度本身就是版本

代价：如果 LEN 因为干扰变成 `px*3`，会被 NACK 而不是被误解。可接受。

## 5. 上位机最小实现（20 行）

想自己写发送端的话，这就是全部核心：

```python
import serial, struct, time
import cv2, numpy as np

MAGIC, ACK, NACK = b"\x55\xAA", 0x06, 0x15

def frame_to_rgb332(bgr, w, h):
    small = cv2.resize(bgr, (w, h), interpolation=cv2.INTER_AREA)
    rgb = cv2.cvtColor(small, cv2.COLOR_BGR2RGB).astype(np.uint16)
    v = ((rgb[:, :, 0] >> 5) << 5) | ((rgb[:, :, 1] >> 5) << 2) | (rgb[:, :, 2] >> 6)
    return v.astype(np.uint8).tobytes()

def send_frame(ser, data, w, h, wait_ack=True):
    pkt = (MAGIC + struct.pack("<HHI", w, h, len(data))
           + data + struct.pack("<H", sum(data) & 0xFFFF))
    for _ in range(4):
        ser.write(pkt)
        if not wait_ack:
            return True
        deadline = time.time() + 3.0
        while time.time() < deadline:
            b = ser.read(1)
            if b and b[0] == ACK:
                return True
            if b and b[0] == NACK:
                break
        ser.reset_input_buffer()
    return False
```

用法：

```python
ser = serial.Serial("COM3", 1500000, timeout=0.2)
cap = cv2.VideoCapture("bad_apple.mp4")
while True:
    ok, frame = cap.read()
    if not ok: break
    send_frame(ser, frame_to_rgb332(frame, 80, 80), 80, 80)
```

**这段代码能跑**，但少了三样东西：cover 裁切（不然 16:9 视频变形）、Bayer 抖动（不然渐变色阶明显）、断线重连。完整版见 `pc_video_sender/video_to_uart.py`。

## 6. 抓包对照

一帧 8×8 的 8 位全黑帧（LEN = 64 = `0x40`），线上真实字节：

```
55 AA              magic
08 00              W = 8        (小端)
08 00              H = 8
40 00 00 00        LEN = 64     (小端)
00 00 ... (64×00)  DATA         (全黑)
00 00              CHECKSUM = 0 (小端)
```

响应：`06`。

一帧 8×8 的 16 位全白帧（LEN = 128 = `0x80`，每像素 `FF FF`）：

```
55 AA 08 00 08 00 80 00 00 00 | FF FF ×64 | 80 7F
```

校验和 = `(255 * 128) & 0xFFFF` = `0x7F80` → 小端存放为 `80 7F`。

> 调试技巧：如果逻辑分析仪抓出来的第一帧是 `55 AA` 后面跟着一堆 `FF`，说明 DC 引脚在帧头阶段被拉高了——SPI 没问题，是 DC 时序错了。

## 7. 为什么不做滑动窗口 / 压缩

都想过，都放弃了，理由记录下来省得后人再想一遍：

| 想法 | 为什么放弃 |
|---|---|
| 滑动窗口（一次发 4 帧再统一确认） | 1.5 Mbps 下 RTT ≈ 1 ms，停等的带宽损失 < 1%。窗口带来的复杂度（乱序、重排、缓冲翻倍）完全不值 |
| RLE 压缩 | 视频帧几乎无连续同色像素，压缩率 < 5%，白忙 |
| 差分帧（只传变化的块） | Bad Apple 这类全屏动画毫无收益；而且解码要额外 RAM |
| JPEG / MJPEG | 解码要 20~40 ms（F407 无硬件 JPEG），比省下来的传输时间还多 |
| 硬件 CRC | 累加和在 6400 B 上只要 ~20 µs，不是瓶颈 |
| 加帧序号 | 定界靠魔数 + 停等协议，不需要序号。加了反而多 2 字节 |

**结论：这套"土"协议在 1.5 Mbps 这个带宽下已经接近最优。** 真要提高帧率，方向是换物理通道（USB CDC / SD 卡），不是优化协议。
