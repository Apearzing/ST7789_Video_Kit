# 用 STM32F407 把 1.3 寸小屏做成视频播放器：一套能移植的串口投屏方案

> 一块 20 块钱的 ST7789 小屏，一根 USB 转串口线，一颗 F407，播 Bad Apple 能跑到 17 fps。
> 本文把整套方案的设计取舍、协议格式、关键代码和移植方法都摊开讲。

---

## 一、先说结论

| 指标 | 数值 |
|---|---|
| 屏 | ST7789 1.3" IPS 240×240，SPI 接口 |
| 主控 | STM32F407VET6，144 MHz |
| 播放帧率 | **80×80 8 位色 @1.5 Mbps ≈ 17 fps**；120×120 ≈ 10 fps |
| 全屏刷新 | 51 ms（SPI 18 MHz） |
| 固件 RAM 占用 | 约 58 KB（双缓冲） |
| 电脑端 | Python + OpenCV，已打包成单文件 exe |

**核心思路一句话**：把重活全留在电脑。电脑负责解码、缩放、量化到 8 位色，一帧只剩 6~14 KB；单片机只做「收字节 → 校验 → 整数倍放大 → 刷屏」，不需要 JPEG 解码、不需要外部 SDRAM、不需要 RTOS。

这套思路的价值不在"能播视频"，而在**它是一条可以移植的路线**——换 MCU、换屏、换通道都能沿用。下面按这个顺序讲。

## 二、硬件与接线

### 2.1 清单

| 器件 | 说明 |
|---|---|

| ST7789 1.3 寸 240×240 IPS | 7 针 SPI（CS/DC/RST/SCL/SDA/VCC/GND）+ BL |

|---|---|---|
| CS | PA0 | 普通 GPIO |
| DC | PA1 | 普通 GPIO |
| RST | PA2 | 普通 GPIO |
| SCL | **PA5** | SPI1_SCK，AF5 复用，不能随便改 |
| SDA | **PA7** | SPI1_MOSI，AF5 复用 |

|---|---|---|

## 三、协议设计：为什么不用 JPEG

一开始我也想过在电脑端压 JPEG、单片机端解码。算完账就放弃了：

| 方案 | 每帧数据 | 单片机成本 |
|---|---|---|
| JPEG 320×240 Q70 | ~8 KB | 解码 30~50 ms（F407 无硬件 JPEG），还可能要外部 RAM 做缓冲 |
| **RGB332 80×80** | **6.4 KB** | **零解码，直接刷** |
| RGB565 80×80 | 12.8 KB | 零解码 |

F407 软解 JPEG 一帧就要 30~50 ms，加上刷屏 51 ms，还不如直接传原始像素。而且 JPEG 解码要几十 KB 的临时缓冲，F407 的 128 KB RAM 会很紧张。

**所以：不压缩，直接把像素降精度。** 8 位色（RGB332）配合抖动，观感完全够用——这是整个方案能成立的前提。

### 3.1 帧格式

```
┌──────┬──────┬───────┬───────┬──────────┬──────────┬──────────┐
│ 0x55 │ 0xAA │ W u16 │ H u16 │ LEN u32  │  DATA    │ CHECKSUM │
└──────┴──────┴───────┴───────┴──────────┴──────────┴──────────┘
       帧头 10 字节（小端）       LEN 字节        2 字节（小端）
```

| 字段 | 说明 |
|---|---|
| magic | 定界用，丢字节后能重新扫描对齐 |
| W / H | 1~120，上位机改分辨率不用改固件 |
| LEN | 必须是 `W*H`（8 位）或 `W*H*2`（16 位） |
| DATA | 行优先；**RGB565 高字节在前**（大端），屏要的就是这个顺序 |
| CHECKSUM | `sum(DATA) & 0xFFFF`，不含帧头 |

**设计里最巧的一处**：位深不写在协议里，靠 `LEN` 反推。

```c
uint32_t px = (uint32_t)w * h;
if (len != px && len != px * 2) { NACK; continue; }
fbpp = (len == px) ? 1 : 2;      /* 1 = RGB332, 2 = RGB565 */
```

好处是：电脑端切 8 位/16 位，**固件一行都不用改、不用重烧**。后来我加 8 位色功能时，固件确实只改了 3 行。

### 3.2 为什么要 ACK

停等协议（发一帧、等一个字节、再发下一帧）听起来很土，但在 1.5 Mbps 下 RTT 只有 1~2 ms，带宽损失不到 1%。换来的是：

- 校验失败自动重传，长线材也不怕
- 电脑端知道单片机有没有跟上，不会无限堆积
- **RX 线没接时能自动降级**（连续 3 帧超时 → 转单向模式），第一次接线少接一根线也能跑

这个自动降级很重要。很多人第一次接线只接了 TX 和 GND，如果没有降级，看到的就是"一直超时 + 画面不动"，会误判成代码有问题。

## 四、固件里的三个关键实现

### 4.1 SPI 必须是 Mode 3

这是移植失败原因的第一名。ST7789 在 SCL **上升沿**采样，而软件模拟 SPI 的波形是「SCK 空闲高 → 拉低时放数据 → 拉高时锁存」，等价于：

```c
hspi1.Init.CLKPolarity = SPI_POLARITY_HIGH;   /* CPOL = 1，空闲高 */
hspi1.Init.CLKPhase    = SPI_PHASE_2EDGE;     /* CPHA = 1，第二个边沿采样 */
/* → Mode 3 */
```

配成 Mode 0（空闲低、第一个边沿采样）的典型症状：**只亮背光 / 满屏花噪 / 偶尔闪一下**。命令根本没被正确接收。

### 4.2 双缓冲让「收」和「显」并行

单缓冲是串行的：收 43 ms → 刷 51 ms → 收 43 ms → 刷 51 ms ≈ **10 fps**。

双缓冲把刷屏塞进"等 DMA"的空隙里：

```
收第 N+1 帧（DMA 后台）  ────────────┐
刷第 N 帧（CPU 前台）    ────────────┤ 并行
                                     ▼
                        一帧耗时 = max(43, 51) = 51 ms → 19 fps
```

代码骨架：

```c
for (;;) {
    /* 1. 扫魔数，拿 8 字节帧头 */
    if (!V_WaitMagic(1500)) { if (有未显示的帧) 刷上去; continue; }
    DMA 收 8 字节帧头;

    /* 2. 校验参数 */
    if (W 或 H 非法 || LEN 不匹配) { NACK; continue; }

    /* 3. 启动 DMA 收数据（后台跑） */
    V_DmaRxStart(back, len);

    /* 4. 关键：趁 DMA 在收，把上一帧刷到屏上 */
    if (haveFront && !frontShown) { ShowImageAuto(front); frontShown = true; }

    /* 5. 等数据、比对校验和 */
    if (!V_DmaRxWait(2500)) continue;
    if (校验失败) { NACK; continue; }

    /* 6. 换缓冲，立刻回 ACK */
    swap(front, back);
    frontShown = false;
    V_TxByte(0x06);
}
```

**第 4 步是整个方案性能的关键**，少了它帧率直接掉一半。

还有一个坑：`HAL_UART_Receive_DMA` 超时后必须 `HAL_UART_Abort`，否则 UART 状态永远停在 BUSY，后续所有接收返回 `HAL_BUSY`，画面永久卡死。症状是"跑几秒就不动了"。

```c
while (HAL_UART_GetState(&huart1) != HAL_UART_STATE_READY) {
    if (HAL_GetTick() - t0 > timeoutMs) {
        HAL_UART_Abort(&huart1);      /* 这行不能少 */
        return false;
    }
}
```

### 4.3 整数倍放大

电脑端发 60~120 px 的小图，屏是 240×240，用最近邻整数倍放大：

```c
for (uint16_t sy = 0; sy < h; sy++) {
    const uint8_t *row = src + sy * w * bpp;
    /* 水平：每个源像素复制 scale 次 */
    for (uint16_t sx = 0; sx < w; sx++) {
        ...
        for (uint8_t k = 0; k < scale; k++)
            s_lineBuf[(sx*scale + k)*2] = hi;
    }
    /* 垂直：同一行发 scale 次 */
    for (uint8_t k = 0; k < scale; k++)
        HAL_SPI_Transmit(&hspi1, s_lineBuf, dw*2, HAL_MAX_DELAY);
}
```

三个要点：

1. `scale` 必须是**整数**。浮点缩放会引入摩尔纹，而且慢十倍。60→4×、80→3×、90→2×、120→2×。
2. 只用 **480 字节**行缓冲（一整行 240 像素 × 2 字节），所以约束是 `w*scale ≤ 240`。这就是源分辨率上限 120 的原因。
3. 8 位色要在单片机端展开成 RGB565，用**位复制**而不是移位，保证 0 变 0、满值变满值：

```c
uint8_t r3 = (v >> 5) & 7, g3 = (v >> 2) & 7, b2 = v & 3;
uint8_t r5 = (r3 << 2) | (r3 >> 1);        /* 3bit → 5bit */
uint8_t g6 = (g3 << 3) | g3;               /* 3bit → 6bit */
uint8_t b5 = (b2 << 3) | (b2 << 1) | (b2 >> 1);
```

## 五、电脑端：把 8 位色做好看

8 位色只有 256 色，直接截断会出现明显色阶（天空变三条带）。这里用 **Bayer 4×4 有序抖动**：

```python
_BAYER4 = np.array([[0, 8, 2, 10], [12, 4, 14, 6],
                    [3, 11, 1, 9], [15, 7, 13, 5]], dtype=np.int16)

t = np.tile(_BAYER4, ((h + 3)//4, (w + 3)//4))[:h, :w]
r = np.clip((rgb[:, :, 0] + t*2 - 15) >> 5, 0, 7)   # 5bit → 3bit
g = np.clip((rgb[:, :, 1] + t*2 - 15) >> 5, 0, 7)
b = np.clip((rgb[:, :, 2] + t*4 - 30) >> 6, 0, 3)   # 蓝色多抖一倍
v[rgb.max(axis=2) < 20] = 0                          # 暗部压纯黑
```

两行经验：

- **蓝色抖动幅度加倍**（`t*4-30` 而不是 `t*2-15`），否则暗部偏紫、亮部偏青
- **最亮通道 <20 的像素直接压纯黑**，黑背景的白噪点立刻消失。这比"暗部减少抖动"有效得多

还有一处容易忽略：**按比例居中裁切**，别拉伸。

```python
s = max(w / vw, h / vh)                                  # cover
rs = cv2.resize(bgr, (int(vw*s), int(vh*s)), interpolation=cv2.INTER_AREA)
small = rs[y0:y0+h, x0:x0+w]                              # 居中裁切
```

用 `INTER_AREA` 而不是 `INTER_LINEAR`：缩小场景下相当于区域平均，抗锯齿而且更快。

## 六、性能账本

调帧率最忌讳"改个参数试试"。先把账算清楚：

```
T_uart = (帧长 + 12) × 10 / 波特率
T_lcd  = 240 × 240 × 2 × 8 / SPI时钟 = 51.2 ms @18 MHz
一帧耗时 = max(T_uart, T_lcd)        ← 双缓冲
```

| 分辨率 | 帧长 | T_uart | T_lcd | 理论 | 实测 |
|---|---|---|---|---|---|
| 60×60 | 3 612 B | 24.1 ms | **51.2 ms** | 19.5 fps | 17 fps |
| 80×80 | 6 412 B | 42.7 ms | **51.2 ms** | 19.5 fps | 17 fps |
| 120×120 | 14 412 B | 96.1 ms | 51.2 ms | 10.4 fps | 10 fps |

**这张表最重要的结论**：60 和 80 的帧率完全一样，因为都被 51.2 ms 的刷屏卡住了。所以——

> 同样的帧率，当然选 80×80，画质好 78%。

很多人第一反应是"降分辨率提速"，但在这套系统里，降到 60 以下**一点用都没有**，因为瓶颈已经从串口换成刷屏了。

要突破 19.5 fps 只有两条路：

1. **提 SPI 时钟**：`/4 → /2`（36 MHz），刷屏 25.6 ms → 理论 23 fps。ST7789 手册标称 15 MHz，36 MHz 属于超频，实测多数屏能跑，但要连续跑 10 分钟验证。
2. **换物理通道**：USB CDC（吞吐 700 KB/s~1 MB/s）或 SD 卡本地播放。

## 七、移植方案

这部分是本文的重点。整套代码按四层切开，哪一层可以换、换起来多麻烦，一目了然。

| 你换了什么 | 改哪层 | 工作量 |
|---|---|---|
| 换 MCU | CubeMX 配置（SPI 分频、DMA 通道号） | 半天 |
| 换屏（同 SPI 接口） | 驱动层（初始化序列 + offset + 分辨率宏） | 1~2 小时 |
| 换传输（USB CDC / SD 卡） | 协议层的收发原语 | 1~2 天 |
| 改分辨率 | 两个宏 | 半小时 |

### 7.1 换 MCU

| MCU | SPI1 引脚 | 可跑分频 | RAM | 注意 |
|---|---|---|---|---|
| F103C8 | PA5/PA7 | /4 = 18 MHz | **20 KB** | RAM 不够，必须降级 |
| F411 | PA5/PA7 | /4 = 25 MHz | 128 KB | 直接可用 |
| G431 | PA5/PA7 | /4 = 42.5 MHz | 32 KB | 建议 80px |
| H743 | PA5/PA7 | /4 = 25 MHz+ | 1 MB | 可开三缓冲 |

**RAM 账要提前算**：双缓冲 = `120×120×2×2 = 57.6 KB`。F103C8 只有 20 KB，直接搬会 HardFault（症状是上电就挂或画面随机花屏，因为栈被挤进缓冲区）。

降级路线（按画质损失排序）：

| 方案 | RAM | 代价 |
|---|---|---|
| A. 分辨率降到 80×80，双缓冲 | 25.6 KB | 画质降，**帧率不变**仍 17 fps |
| B. 80×80 单缓冲 | 12.8 KB | 帧率掉到 ~9 fps（收显串行） |
| C. 80×80 8 位 + 单缓冲 | 6.4 KB | ~14 fps，色彩差 |

方案 A 只改两个宏，是首选。

### 7.2 换屏

| 屏 | 改什么 |
|---|---|
| **ST7735** 128×160 | 分辨率宏 + `X_OFFSET=2`/`Y_OFFSET=1`（按现象试）+ 完整替换初始化序列（需要 0x B1/B2/B3 帧率控制、C0~C4 电源）。MADCTL 四个方向试 `0x00`/`0xC0`/`0x60`/`0xA0` |
| **ILI9341** 240×320 | 分辨率宏 + offset 都是 0 + 更换初始化序列（电源 CF/ED/E8/CB/F7 + gamma E0/E1）。注意全屏 153 600 B，18 MHz 下 68 ms → 上限 14.6 fps |
| **GC9A01** 240×240 圆屏 | 分辨率/窗口逻辑全不变，**只换初始化序列**（约 40 条魔法数，抄厂商 demo） |
| **SSD1306** 128×64 | **不建议**。1bpp + 页寻址，协议层要重写 |

换屏的通用判断工具是"方向卡"：上电先画四边四色 + 上下箭头，4 秒内就能确认 MADCTL 和 offset 对不对。

```
┌────────────────┐  ← 红条 + 上箭头 = 方向正确
│  ↑             │
│  █  (中心圆)   │
│  ↓             │
└────────────────┘  ← 蓝条 + 下箭头
```

红条在上 → `0x36` 参数对；上下颠倒 → `0x00` 改 `0xC0`。**先点亮方向卡，再谈视频**，顺序反了会浪费一整天。

### 7.3 换通道

**UART → USB CDC**（最值得做的一次升级）：

| 项 | UART + DMA | USB CDC |
|---|---|---|
| 接收单位 | 一次 28 800 B | 每包最多 **64 B** |
| 完成通知 | DMA 传输完成中断 | `CDC_Receive_FS()` 回调 |
| 定长接收 | `HAL_UART_Receive_DMA(p, len)` | 没有，要自己攒环形缓冲 |

改法：加 64 KB 环形缓冲，把 `V_DmaRxStart/V_DmaRxWait` 换成「从环里取 N 字节，够不够 / 超时没有」，**帧校验逻辑一行不用改**。

**UART → SD 卡本地播放**（最推荐的产品化路线）：电脑端离线把视频转成定长帧序列 `.bin`，固件用 FATFS `f_lseek` 定位 + `f_read` 读帧 + 刷屏。插卡就播，帧率恒定，去掉电脑这个不稳定因素。

## 八、踩坑清单

按出现频率排序，都是真踩过的：

| # | 症状 | 原因 | 处理 |
|---|---|---|---|
| 1 | 花屏 / 只亮背光 | SPI 配成 Mode 0 | 改 CPOL=High + CPHA=2Edge |
| 2 | 完全没反应 | SCL/SDA 还在 PA3/PA4 | 改到 PA5/PA7（AF5） |
| 3 | 顶部黑边 / 画面偏移 | `Y_OFFSET` 不对 | 试 0 / 40 / 80 |
| 4 | 颜色反相 | `0x21` (INVON) 该不该留 | 逐屏试，注掉或加上 |
| 5 | 画面卡在第一帧 | 波特率只改了一边 | `usart.c` 和界面必须一致 |
| 6 | 跑几秒就卡死 | 超时没 `HAL_UART_Abort` | 见 §4.2 |
| 7 | 偶发花屏 / 缺块 | 杜邦线太长 @1.5 Mbps | 换短线或降到 921600 |
| 8 | 有画面但一直 NACK | RXD→PA9 回线松了 | 重插，或关 ACK |
| 9 | 一帧都收不到 | 忘接 GND | 共地 |
| 10 | 上电就 HardFault | RAM 溢出（双缓冲太大） | 降分辨率，看 .map |

## 九、分层点亮：正确的调试顺序

移植最容易犯的错是"全部接好、一次烧录、什么都不亮、不知道哪层错了"。正确顺序：

| 步骤 | 做什么 | 验收标准 |
|---|---|---|
| 1 | 只配 SPI，循环发数据 | 逻辑分析仪看到 PA5 有 18 MHz 方波 |
| 2 | `Init()` + `Clear(RED)` | 整屏纯红 |
| 3 | 方向卡 | 红条在上、箭头朝上 |
| 4 | `ShowImageScale` 画棋盘格 | 4× 放大铺满、无错位 |
| 5 | 协议层，手工发一帧纯色 | ACK 回 0x06，图案出现 |
| 6 | 上位机推视频 | 连播 10 分钟不花不卡 |

第 5 步的调试技巧：写 20 行 Python 只发一帧纯色，比一开始就推视频好定位一百倍。

```python
import serial, struct
W = H = 60
data = bytes([0x07] * (W*H))          # RGB332
pkt = b"\x55\xAA" + struct.pack("<HHI", W, H, len(data)) + data \
      + struct.pack("<H", sum(data) & 0xFFFF)
serial.Serial("COM3", 1500000).write(pkt)
```

## 十一、写在最后

这个项目技术上没什么高深的：一个自定义串口协议、一个 SPI 屏驱动、一个 Python 脚本。真正花时间的是**把每个参数的"为什么"弄清楚**——为什么必须 Mode 3、为什么 60 和 80 帧率一样、为什么 8 位色要抖动、为什么超时后必须 Abort。

这些东西不写下来，下次换块板子还得重踩一遍。所以把它们整理成了一份移植文档，希望能让后来的人少走一点弯路。

如果这篇对你有帮助，点个赞让更多人看到；有问题评论区聊，接线和花屏的问题基本都能凭现象定位。
