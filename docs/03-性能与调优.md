# 性能与调优：帧率是怎么算出来的

> 调帧率最忌讳"改一个参数试试"。先把账算清楚，你知道天花板在哪，就不会在错误的方向上折腾。

---

## 1. 两个天花板

这套系统的每一帧都要过两道关，**总时间是两者的最大值**（双缓冲），不是和：

```
   串口传输 T_uart  ─────┐
                         ├──► 一帧耗时 = max(T_uart, T_lcd)
   刷屏     T_lcd   ─────┘
```

```c
T_uart = (帧长 + 12) × 10 / 波特率          /* 10 = 起始 + 8 数据 + 停止 */
T_lcd  = 240 × 240 × 2 × 8 / SPI时钟        /* 全屏 115200 B，与源分辨率无关 */
```

代入本项目的参数：

| 关卡 | 数值 |
|---|---|
| 串口 @1.5 Mbps | 150 000 B/s |
| 刷屏 @18 MHz | 460 800 bit ÷ 18 MHz = **51.2 ms** |

**刷屏 51.2 ms → 19.5 fps 是硬上限。** 记住这个数，后面所有讨论都围绕它。

---

## 2. 帧率账本

### 2.1 1.5 Mbps + 18 MHz SPI，8 位色（默认配置）

| 分辨率 | 帧长 | T_uart | T_lcd | 理论帧率 | 实测 |
|---|---|---|---|---|---|
| 60×60 | 3 612 | 24.1 ms | **51.2 ms** | 19.5 fps | **≈17 fps** |
| 80×80 | 6 412 | 42.7 ms | **51.2 ms** | 19.5 fps | **≈17 fps** |
| 90×90 | 8 112 | 54.1 ms | 28.8 ms¹ | 18.5 fps | —² |
| 120×120 | 14 412 | 96.1 ms | 51.2 ms | 10.4 fps | **≈10 fps** |

¹ 90×90 只放大 2× 到 180×180，不是全屏，所以刷屏更快。
² 早期记录里的 "90 ≈ 9 fps" 是 16 位色口径，8 位色下应接近 17 fps，未单独标定。

**这张表最重要的结论**：60 和 80 的帧率**完全一样**，因为两者都被 51.2 ms 的刷屏卡住了。所以——

> **同样的帧率，当然选 80×80：画质好 78%，帧率不变。**

这也是把默认分辨率从 60 改成 80、后来又从 80 改成 120 的原因：真正该权衡的是「画质 vs 帧率」，而不是「分辨率越低越快」。

### 2.2 16 位色（画质优先）

| 分辨率 | 帧长 | T_uart | 理论帧率 | 实测 |
|---|---|---|---|---|
| 60×60 | 7 212 | 48.1 ms | 19.5 fps | ≈17 fps |
| 80×80 | 12 812 | 85.4 ms | 11.7 fps | ≈11 fps |
| 120×120 | 28 812 | 192.1 ms | 5.2 fps | **≈5 fps** |

16 位的代价是数据量翻倍，在 120×120 上直接把帧率砍到 5 fps。**除非在放静态图片或色彩要求高的内容，否则用 8 位。**

### 2.3 不同波特率（8 位，80×80）

| 波特率 | T_uart | 瓶颈 | 理论帧率 | 备注 |
|---|---|---|---|---|
| 921 600 | 69.5 ms | 串口 | 14.4 fps | 最稳，所有模块都支持 |
| 1 500 000 | 42.7 ms | 刷屏 | 19.5 fps | **默认**，CH340 基本都行 |
| 2 000 000 | 32.0 ms | 刷屏 | 19.5 fps | 再快也没用，已经撞到刷屏 |
| 3 000 000 | 21.4 ms | 刷屏 | 19.5 fps | 多数 USB-TTL 不支持，白折腾 |

**这张表说明**：在 18 MHz SPI 下，波特率提到 1.5 Mbps 之后就没有意义了——瓶颈已经换成刷屏。想再快，**必须动 SPI**。

## 3. 瓶颈定位：三步法

改任何参数之前先做这三步，省半小时。

### 第一步：算一下谁是大头

```
T_uart vs T_lcd，谁大谁就是瓶颈
```

- `T_uart > T_lcd` → 瓶颈在串口 → 降分辨率、降色彩深度、提波特率
- `T_uart < T_lcd` → 瓶颈在刷屏 → **降分辨率完全没用**，只能提 SPI 时钟或换传输

### 第二步：看固件是不是在"等"

在 `Video_Loop()` 里临时加两个翻转：

```c
HAL_GPIO_TogglePin(GPIOD, GPIO_PIN_8);   /* 进循环翻一次 */
... 收帧 ...
HAL_GPIO_TogglePin(GPIOD, GPIO_PIN_8);   /* 收完再翻一次 */
```

逻辑分析仪看 PD8 的周期：**等于 `max(T_uart, T_lcd)` 就说明流水线是满的**（设计正确）；明显大于这个值，说明有空转（通常是 ACK 等待或超时重试）。

### 第三步：区分"慢"和"卡"

| 现象 | 含义 | 查什么 |
|---|---|---|
| 帧率稳定但低 | 带宽/刷屏到顶 | 算账，见上 |
| 帧率忽高忽低 | ACK 重传 | 看日志有没有 "ACK timeout" / "NACK" |
| 画面延迟越来越大 | 发送比消费快 | 单向模式的 pacing 下限（0.06 s）丢了 |
| 播几十秒后停住 | 状态机卡死 | UART 超时没 `HAL_UART_Abort` |

## 4. 优化路线（按投入产出排序）

### 4.1 零成本（改参数就有）

| 改动 | 收益 | 代价 |
|---|---|---|
| 分辨率 60 → 80 | 帧率不变，画质 +78% | 无 |
| 色彩 16 位 → 8 位 | 帧率 ×2 | 有轻微噪点，远看无感 |
| 勾上「等待 ACK」 | 比单向快 10~20%，且有重传 | 需要接 RX 线 |
| 换短杜邦线 | 少丢包，少重传 | 无 |
| 用对比强、节奏慢的片源 | 同帧率下主观流畅度大幅提升 | 无 |

> 最后一条不是玄学。Bad Apple 这种黑白剪影在 8 位色 + 抖动下几乎无损，而实拍彩色视频在 8 位色下会明显发脏——**片源选择比参数调整更能决定"看起来流不流畅"**。

### 4.2 小改（改两行代码）

**SPI 分频 /4 → /2（36 MHz）**

```c
hspi1.Init.BaudRatePrescaler = SPI_BAUDRATEPRESCALER_2;   /* 72/2 = 36 MHz */
```

- 刷屏 51.2 ms → **25.6 ms**
- 80×80 8 位：瓶颈变成串口 42.7 ms → **理论 23.4 fps，实测约 20 fps（+18%）**
- 风险：ST7789 手册标称写周期 66 ns（≈15 MHz），36 MHz 属于超频。实测多数屏能跑，但要连续跑 10 分钟验证，尤其注意**温度上来之后**是否偶发花屏

**继续往上**：/2 是 F407 在 72 MHz APB2 下的极限（没有更小的分频了）。想再快只能提 APB2 时钟（到 84 MHz → /2 = 42 MHz），或者换 H7/G4。

### 4.3 中改（换通道）

| 方案 | 理论帧率 | 工作量 | 说明 |
|---|---|---|---|
| **USB CDC** | 显示上限 19.5 fps @18 MHz；SPI 36 MHz 时 39 fps | 1~2 天 | 吞吐 700 KB/s~1 MB/s，彻底解决串口瓶颈 |
| **SD 卡本地播放** | 同显示上限 | 2~3 天 | 去掉电脑，成品感最强，帧率恒定 |
| **以太网 / WiFi** | 同显示上限 | 3~5 天 | 除非要远程投屏，否则不值 |

详见 [01-移植方案.md §6.3](01-移植方案.md)。

### 4.4 大改（换硬件架构）

| 方案 | 帧率 | 说明 |
|---|---|---|
| SPI DMA + 双行缓冲 | +5~10% | 现在 `HAL_SPI_Transmit` 阻塞 CPU，改 DMA 后 CPU 能去算校验和。收益不大，**不建议现在做** |
| RGB 并口屏（FSMC/LTDC） | 60 fps+ | 换屏 + 换驱动 + 换接线，等于重做。真要到这一步，不如直接上 ESP32 + LVGL |
| ST7789 局部刷新 | 视内容 | 只发改动的矩形区域。Bad Apple 这类全屏动画收益为 0，静态 UI 收益巨大 |

**关于 SPI DMA 的取舍**：把 `HAL_SPI_Transmit` 换成 `HAL_SPI_Transmit_DMA` + 半传输中断，能让 CPU 在刷屏的 51 ms 里去处理串口。但当前架构下串口是 DMA 后台收的，CPU 本来就闲着——所以收益只有"校验和算得更早"这一项，5% 左右。**复杂度翻倍换 5%，不划算**，除非你打算上双屏或者加复杂 UI。

## 5. 为什么实测总比理论低 10~15%

80×80 理论 19.5 fps，实测 17 fps，差的这 2.5 fps 花在哪：

| 开销 | 量级 |
|---|---|
| 协议头 + 校验和 | 12 B / 6412 B ≈ 0.2% |
| ACK 往返（3 ms 超时窗口内的实际 RTT） | 1~2 ms |
| Python 端 `cv2.resize` + 量化 + 打包 | 80px 约 1.5~3 ms |
| `serial.write` 分块（Windows 每 4 KB 一次系统调用） | 0.5~1 ms |
| ACK 后到下一次 DMA 启动之间的空隙 | < 1 ms |
| 固件校验和 6400 B 累加 | ~30 µs（可忽略） |

主要开销在**上位机**，不在固件。如果想让帧率更贴近理论，优化 Python 端比优化 C 端有效：

```python
# 1. 用 cv2.resize 的 INTER_NEAREST 代替 INTER_AREA（缩小倍率大时几乎无差别，快 3 倍）
# 2. 量化用 numpy 向量化，别写 Python 循环
# 3. 串口 write 前把 pkt 用 bytearray 拼好，避免多次 bytes 拼接
# 4. 用 --fps 0 让 ACK 决定节拍，别额外 sleep
```

## 6. 画质调优：8 位色抖动参数演进史

这一节是踩坑记录，不是理论。8 位色（RGB332）只有 256 色，量化方式直接决定"能不能看"。

| 版本 | 做法 | 结果 | 结论 |
|---|---|---|---|
| v0 | 直接截断 `>>5` | 渐变色出现明显色阶，天空变三条带 | 太脏 |
| v1 | 全额 Bayer 4×4 抖动 | 色彩过渡自然，但黑背景全是白噪点 | 方向对，暗部有问题 |
| v2 | 抖动强度随亮度衰减 | 白噪点减少，但暗部发灰 | 折中不够 |
| v3 | 回退到无抖动 | 噪点没了，画面回扁平 | 不能接受 |
| **v4** | **全额抖动 + 最亮通道 <20 压纯黑** | 过渡自然，黑底干净 | **当前方案** |

关键的两行：

```python
# 抖动幅度：红绿 5bit→3bit 抖 ±15，蓝色 5bit→2bit 抖 ±30（蓝色更不敏感，多抖）
r = np.clip(((rgb[:,:,0] + t*2 - 15) >> 5), 0, 7)
b = np.clip(((rgb[:,:,2] + t*4 - 30) >> 6), 0, 3)

# 暗部压黑：不是"低于阈值就少抖"，而是"直接纯黑"，白噪点才能真正消失
v[rgb.max(axis=2) < 20] = 0
```

**经验**：

1. 蓝色通道的抖动幅度必须**比其他通道大一倍**，否则暗部偏紫、亮部偏青
2. 抖动矩阵用 `np.tile` 平铺到整帧，别用循环——这是 Python 端最大的一笔性能开销
3. 「暗部压黑」比「暗部减抖」有效得多，因为噪点的视觉权重在纯黑背景上最高
4. 抖动一定会在近看时有细颗粒，**离远看是对的**——1.3 寸屏的正常观看距离是 20 cm 以上

## 7. 怎么准确测帧率

别凭感觉，三种方法从粗到细：

**方法 1：上位机日志（最方便，含所有开销）**

```python
if n % 30 == 0:
    print(f"{n} frames, {n / (time.time() - t0):.1f} fps")
```

测出来的就是"用户感受到的帧率"，**推荐用这个作为唯一指标**。

**方法 2：固件打点（看固件内部节拍）**

PD8 每帧翻转一次，逻辑分析仪测周期。如果周期 = `T_lcd`，说明固件是满负荷的，慢在上位机；如果周期 > `T_lcd`，说明固件在等数据。

**方法 3：秒表法（最土但最可信）**

放一段 10 秒的固定内容，数屏上播完用了多久。视频 10 秒、实际播了 25 秒 → 2.4 fps。这个方法能抓到"日志显示 17 fps 但画面明显不同步"这类问题（通常是丢帧但 ACK 正常）。

## 8. 一句话总结

> **18 MHz 下刷屏 51.2 ms 就是天花板（19.5 fps）。想清楚瓶颈是串口还是刷屏，再决定降分辨率还是提 SPI——搞反了会白忙一天。**
