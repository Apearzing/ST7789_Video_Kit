# 移植方案：把 ST7789 串口视频这套东西搬到你的板子上

> 本文是这套方案的**工程说明书**。目标不是"复制粘贴能跑"，而是让你清楚每一个参数为什么是那个值，换 MCU、换屏、换通道时知道该动哪一行。

---

## 0. 先认清这套系统由什么组成

四层，从下往上：

```
┌─────────────────────────────────────────────────────────┐
│ 应用层   main.c        方向卡 → 等流 → 循环播放           │  ← 业务，随便改
├─────────────────────────────────────────────────────────┤
│ 协议层   video_player  帧解析 + 校验 + 双缓冲 + ACK/NACK  │  ← 与屏无关，最值钱
├─────────────────────────────────────────────────────────┤
│ 驱动层   st7789_hspi   命令/数据/窗口/整屏整行发送         │  ← 换屏只改这里
├─────────────────────────────────────────────────────────┤
│ 外设层   CubeMX        SPI1(18M,Mode3) + USART1(1.5M,DMA) │  ← 换 MCU 只改这里
└─────────────────────────────────────────────────────────┘
                    ▲
                    │ UART 1.5 Mbps
                    ▼
┌─────────────────────────────────────────────────────────┐
│ 上位机   video_to_uart.py  取帧→裁切→量化→打包→流控        │
└─────────────────────────────────────────────────────────┘
```

**移植的关键判断**：

| 你换了什么 | 要改的层 | 工作量 |
|---|---|---|
| 换 MCU（同系列或换系列） | 外设层（CubeMX 配置）+ DMA 通道号 | 半天 |
| 换屏幕（同 SPI 接口） | 驱动层（初始化序列 + offset + 分辨率宏） | 1~2 小时 |
| 换传输（UART → USB CDC / SD 卡） | 协议层的收发原语 | 1~2 天 |
| 改分辨率 / 非正方形 | 宏 + 缩放函数 | 半小时 |
| 加功能（进度条、菜单） | 应用层 | 随便 |

**协议层和上位机是这个项目里最不该动的东西**——它是屏幕无关、MCU 无关的。所以移植时先把驱动点亮，再把协议接上，不要一上来就改协议。

## 1. 第一步：外设配置（CubeMX）

以 STM32F407VET6 + SPI1 + USART1 为基准。

### 1.1 时钟树

| 项 | 值 | 说明 |
|---|---|---|
| HSE | 8 MHz | 板载晶振 |
| PLLM / PLLN / PLLP | 4 / 144 / 2 | → SYSCLK = 144 MHz |
| AHB | /1 → 144 MHz | |
| APB1 | /4 → 36 MHz | USART1 在 APB2，不受影响 |
| APB2 | /2 → **72 MHz** | SPI1 时钟源 |
| Flash 等待周期 | 4 WS | 144 MHz 必须 |

> 为什么不用满 168 MHz？144 MHz 是「/4 分频刚好得到 9 MHz、/8 得到 4.5 MHz」这类整数关系的舒适区，早期调 SPI 分频时省事。跑 168 MHz 也完全可以，只是 SPI 分频要重新算。

### 1.2 SPI1 参数（**最容易错的地方**）

| 参数 | 值 | 为什么 |
|---|---|---|
| Mode | Master | 屏是从机 |
| Direction | 2 Lines（全双工） | 屏幕一般没有 MISO，但全双工模式配置简单，PA6 悬空即可 |
| Data Size | 8 bit | 每次发一个字节，16 位色由软件拆高低字节 |
| First Bit | MSB | ST7789 要求高位先出 |
| **Clock Polarity** | **High** | 空闲电平为高 |
| **Clock Phase** | **2 Edge** | 第二个边沿（上升沿）采样 |
| → 即 **Mode 3** | | **配 Mode 0 必花屏或黑屏** |
| NSS | Software | CS 自己用 GPIO 控制 |
| Prescaler | **/4** → 18 MHz | 72 / 4 = 18 MHz，稳定；/8 = 9 MHz 更保守 |
| CRC | Disable | 不用 |

**为什么必须是 Mode 3？** 因为这套驱动是从"软件模拟 SPI"版本移植来的，软件版的时序是：

```
SCK 空闲高 ──┐  ┌──┐  ┌──
             └──┘  └──┘
MOSI  ─────< 数据稳定 >────
              ↑ 上升沿锁存
```

`CPOL=High`（空闲高）+ `CPHA=2Edge`（第二个边沿=上升沿采样）正好等价。配成 Mode 0（空闲低、第一个边沿采样）时，从机会在数据还没稳定的位置采样 → 命令全乱 → 花屏 / 黑屏 / 只亮背光。**这是本方案移植失败原因的第一名。**

### 1.3 GPIO

| 引脚 | 模式 | 速度 | 初值 | 用途 |
|---|---|---|---|---|
| PA0 | Output PP | High | SET | CS（片选，低有效） |
| PA1 | Output PP | High | RESET | DC（0=命令，1=数据） |
| PA2 | Output PP | High | SET | RST |
| PA5 | AF PP / AF5 | Very High | — | SPI1_SCK |
| PA6 | AF PP / AF5 | Very High | — | SPI1_MISO（悬空） |
| PA7 | AF PP / AF5 | Very High | — | SPI1_MOSI |
| PD8 | Output PP | Low | — | 板载 LED（可选，心跳） |

### 1.4 USART1

| 参数 | 值 |
|---|---|
| Baud | **1 500 000** |
| Word / Stop / Parity | 8 / 1 / None |
| Mode | TX_RX（回 ACK 需要 TX） |
| Oversampling | 16 |
| DMA | USART1_RX → DMA2 Stream2 Channel4，**Normal 模式**（不是 Circular） |
| NVIC | DMA 中断使能（`ForceEnableDMAVector`） |

> **波特率必须和上位机一致**。只改一边的症状是"画面卡在第一帧不动"——不是花屏，是压根没在收。

### 1.5 生成代码的注意事项

- `Code/` 目录放在 CubeMX 的 **USER CODE 之外**，重新 GENERATE 不会覆盖
- `main.c` 里的调用写在 `USER CODE BEGIN 2` 段内
- 每次重新生成后检查 `spi.c` 的 `BaudRatePrescaler` 和 `usart.c` 的 `BaudRate` 有没有被 CubeMX 改回去

## 2. 第二步：驱动层移植（软件 SPI → 硬件 SPI）

### 2.1 移植的本质：只替换一个原语

软件版和硬件版的**所有上层函数完全同名同签名**，因为差异只有一处：

```c
/* 软件版：翻转 GPIO，一个 bit 一个 bit 推 */
void ST7789_SPI_SendByte(uint8_t dat) {
    for (uint8_t i = 0; i < 8; i++) {
        SCL_LOW();
        if (dat & 0x80) SDA_HIGH(); else SDA_LOW();
        SCL_HIGH();          /* 上升沿，屏采样 */
        dat <<= 1;
    }
}

/* 硬件版：交给 SPI 外设，一行搞定 */
void ST7789_SPI_SendByte(uint8_t dat) {
    HAL_SPI_Transmit(&hspi1, &dat, 1, HAL_MAX_DELAY);
}
```

初始化序列、窗口逻辑、画点画矩形**一行都不用改**。这就是当初把驱动写成"SendByte 原语 + 上层组合"的好处：换总线只动 3 行。

### 2.2 DC / CS 的时序（第二容易错的地方）

```c
static inline void ST7789_DC_Cmd(void)   /* 命令：DC=0，然后 CS=0 */
{
    HAL_GPIO_WritePin(GPIOA, GPIO_PIN_1, GPIO_PIN_RESET);  /* DC 先稳 */
    HAL_GPIO_WritePin(GPIOA, GPIO_PIN_0, GPIO_PIN_RESET);  /* CS 后拉 */
}
```

**顺序不能反**。如果先拉 CS 再改 DC，从机会把 CS 下降沿那一刻的 DC 电平当作本次传输的类型——但更糟的是某些批次屏会在第一个时钟沿就锁存 DC，导致命令被当数据写进 RAM。规矩就一句：**DC 永远在 CS 之前稳定**。

发送结束立刻 `CS = 1`。ST7789 支持 4-line SPI 的 CS 常低模式，但常低时如果 DC 切换不够快，会出现"命令和数据粘在一起"的诡异花屏。本驱动选择**每条命令/每行像素都完整拉一次 CS**，慢一点点，但绝对可靠。

### 2.3 从"逐字节"升级到"整行整包"

这是硬件 SPI 带来的**最大性能收益**，也是移植时最值得做的一步。

软件版清屏：`240×240 = 57600` 次 `SendByte`，每次 8 次 GPIO 翻转 ≈ **276 万次操作**，慢到没法看。

硬件版清屏：**一次准备 480 字节的行缓冲，然后 240 次 `HAL_SPI_Transmit`**：

```c
static uint8_t s_lineBuf[ST7789_W * 2];   /* 480 B */

void ST7789_Clear(uint16_t color) {
    /* 1. 把一行填满同一个颜色 */
    for (uint16_t i = 0; i < ST7789_W; i++) {
        s_lineBuf[2*i]   = color >> 8;
        s_lineBuf[2*i+1] = color & 0xFF;
    }
    ST7789_SetWindow(0, 0, 239, 239);
    DC_DATA(); CS_LOW();
    /* 2. 同一行发 240 次，CS 全程拉低 */
    for (uint16_t row = 0; row < ST7789_H; row++)
        HAL_SPI_Transmit(&hspi1, s_lineBuf, sizeof(s_lineBuf), HAL_MAX_DELAY);
    CS_HIGH();
}
```

**原理**：ST7789 收到 `RAMWR(0x2C)` 后会按窗口自动推进地址，只要数据不断流、CS 不抬起来，就一直往下一个像素写。所以"整行一次发"和"整屏一次发"对屏来说没有区别，只是我们受限于 RAM 只能一次发一行。

效果：全屏 115 200 字节 ÷ 18 MHz ≈ **51.2 ms**（软件 SPI 时代是 100+ ms）。

### 2.4 缩放显示函数（视频部分的核心）

上位机发过来的是小图（60~120 px），要在 240×240 上铺满，用**最近邻整数倍放大**：

```c
void ST7789_ShowImageScale(const uint8_t *src, uint16_t w, uint16_t h,
                           uint8_t scale, uint8_t bpp)
{
    /* 目标尺寸 = 源尺寸 × 整数倍，居中 */
    uint16_t dw = w * scale, dh = h * scale;
    uint16_t x0 = (240 - dw) / 2, y0 = (240 - dh) / 2;

    ST7789_SetWindow(x0, y0 + ST7789_Y_OFFSET, x0 + dw - 1, y0 + dh - 1 + ST7789_Y_OFFSET);
    DC_DATA(); CS_LOW();

    for (uint16_t sy = 0; sy < h; sy++) {
        const uint8_t *row = src + (uint32_t)sy * w * bpp;
        /* 水平方向：每个源像素复制 scale 次 */
        for (uint16_t sx = 0; sx < w; sx++) {
            uint8_t hi, lo;
            if (bpp == 1)      { RGB332_Expand(row[sx], &hi, &lo); }  /* 见 §2.4 末 */
            else               { hi = row[sx*2]; lo = row[sx*2+1]; }
            for (uint8_t k = 0; k < scale; k++) {
                s_lineBuf[(sx*scale + k)*2]     = hi;
                s_lineBuf[(sx*scale + k)*2 + 1] = lo;
            }
        }
        /* 垂直方向：同一行发 scale 次 */
        for (uint8_t k = 0; k < scale; k++)
            HAL_SPI_Transmit(&hspi1, s_lineBuf, dw*2, HAL_MAX_DELAY);
    }
    CS_HIGH();
}
```

几个要点：

1. **`scale` 必须是整数**，浮点缩放会引入摩尔纹而且慢十倍。60→4×、80→3×、90→2×、120→2× 都正好铺满或居中。
2. **`s_lineBuf` 只有 480 B**，所以约束是 `dw ≤ 240`。这就是为什么源分辨率上限是 120（120×2=240）。
3. **8 位色要在单片机端展开成 RGB565**（`bpp == 1` 分支），因为屏只认 16 位。展开用位复制而不是移位，保证 0 变 0、满值变满值：

```c
uint8_t r3 = (v >> 5) & 7, g3 = (v >> 2) & 7, b2 = v & 3;
uint8_t r5 = (r3 << 2) | (r3 >> 1);        /* 3bit → 5bit */
uint8_t g6 = (g3 << 3) | g3;               /* 3bit → 6bit */
uint8_t b5 = (b2 << 3) | (b2 << 1) | (b2 >> 1);
```

### 2.5 行偏置（换屏必调）

ST7789 的显存是 240×320，240×240 的屏只是"切"了其中一段，切的位置由屏厂决定：

```c
#define ST7789_X_OFFSET  0
#define ST7789_Y_OFFSET  0     /* 有黑边就试 40 / 80 */
```

现象对照：

| 现象 | 原因 | 处理 |
|---|---|---|
| 顶部有黑边 | 实际显示区在更下面 | `Y_OFFSET` 增大（0→40→80） |
| 底部有黑边 / 底部错位 | offset 太大 | `Y_OFFSET` 减小 |
| 左右各有一条 | 通常不是 offset | 检查分辨率宏，或 `X_OFFSET` |

## 3. 第三步：协议层移植（双缓冲 + DMA）

这是性能的第二个来源，也是从"能显示"到"能播视频"的分水岭。

### 3.1 为什么需要双缓冲

单缓冲的流程是串行的：

```
收 40 ms  ──► 刷屏 51 ms ──► 收 40 ms ──► 刷屏 51 ms      ≈ 11 fps
```

双缓冲把两者重叠：

```
收 40 ms ──┬─► 收下一帧 40 ms ──┬─► ...
刷屏 51 ms ┘                    └── 刷这一帧
        ↑ 两者并行，总时间 = max(40, 51) = 51 ms        ≈ 19 fps
```

实现上就是两块 28 800 B 的 buf 交替 `front` / `back`，DMA 收 `back`，CPU 刷 `front`：

```c
static uint8_t s_bufA[VIDEO_MAX_W * VIDEO_MAX_H * 2];   /* 28800 B */
static uint8_t s_bufB[VIDEO_MAX_W * VIDEO_MAX_H * 2];
```

**代价**：57.6 KB 静态 RAM。F407 有 128 KB 没问题，F103C8 只有 20 KB，直接搬会 HardFault——见 §7 的降级方案。

### 3.2 DMA 接收的三个坑

**坑 1：必须等上一次 DMA 结束才能启动下一次**

```c
static bool V_DmaRxWait(uint32_t timeoutMs) {
    uint32_t t0 = HAL_GetTick();
    while (HAL_UART_GetState(&huart1) != HAL_UART_STATE_READY) {
        if (HAL_GetTick() - t0 > timeoutMs) {
            HAL_UART_Abort(&huart1);      /* 超时必须 Abort，否则永久 BUSY */
            return false;
        }
    }
    return true;
}
```

不 `Abort` 的后果：超时后状态机永远停在 BUSY，后续所有 `HAL_UART_Receive_DMA` 返回 `HAL_BUSY`，画面永久卡死。**这是移植后"跑一会儿就不动了"的头号原因。**

**坑 2：溢出标志 ORE 必须清**

1.5 Mbps 下只要 CPU 被 SPI 刷屏占住超过 ~7 个字节时间，串口就会溢出。不清 ORE 的话 HAL 会一直返回错误：

```c
__HAL_UART_CLEAR_OREFLAG(&huart1);
```

本方案在"等魔数"的轮询里每轮都清一次，正好利用这段空闲时间把溢出消化掉。

**坑 3：DMA 长度必须是实际帧长**

```c
if (!V_DmaRxStart(back, len)) continue;      /* len 从帧头读出来 */
```

不要图省事固定收 `VIDEO_MAX_W*VIDEO_MAX_H*2`，否则短帧会等后续字节，一直等到超时。

### 3.3 状态机

```
        ┌──────────────┐
        │ 扫魔数 55 AA │◄──────────────────┐
        └──────┬───────┘                   │
               │ DMA 收 8 B 帧头            │
        ┌──────▼───────┐   参数非法         │
        │ 校验 W/H/LEN ├───────────────────┤ NACK
        └──────┬───────┘                   │
               │ DMA 收 LEN 字节            │
        ┌──────▼───────┐   校验错           │
        │ 并行：刷上一帧│───────────────────┤ NACK
        │ 同时：等 DMA   │                   │
        └──────┬───────┘                   │
               │ 收 2 B 校验和，比对通过      │
        ┌──────▼───────┐                   │
        │ 交换 front/back│                  │
        │ 回 ACK (0x06) │                   │
        └──────┬───────┘                   │
               └───────────────────────────┘
```

伪代码（完整实现见 `Code/video_player.c`）：

```c
for (;;) {
    /* 1. 拿帧头：首帧魔数已被消耗，后续每帧先扫魔数 */
    if (first) { DMA 收 8 B; first = false; }
    else {
        if (!V_WaitMagic(1500)) {          /* 1.5 s 没数据 = 流停了 */
            if (有未显示的帧) 刷上去;        /* 断流保持最后一帧 */
            continue;
        }
        DMA 收 8 B;
    }

    /* 2. 解析并校验参数 */
    w, h, len = 解析(hdr);
    if (w == 0 || w > 120 || len != w*h && len != w*h*2) { NACK; continue; }

    /* 3. 启动 DMA 收数据（后台跑） */
    V_DmaRxStart(back, len);

    /* 4. 关键：趁 DMA 在收，把上一帧刷到屏上 */
    if (haveFront && !frontShown) { ShowImageAuto(front); frontShown = true; }

    /* 5. 等数据 + 校验 */
    if (!V_DmaRxWait(2500)) continue;
    收 2 B 校验和;
    if (checksum(back, len) != rxChk) { NACK; continue; }

    /* 6. 换缓冲，立刻 ACK */
    swap(front, back);
    fbpp = (len == w*h) ? 1 : 2;      /* 长度自适应位深 */
    frontShown = false;
    V_TxByte(0x06);
}
```

**第 4 步是整个方案性能的关键**：把"刷屏"塞进"等 DMA"的窗口里。少了这一步，帧率直接掉一半。

### 3.4 位深自适应

同一套协议同时支持 8 位和 16 位，靠的是**帧长度反推**：

```c
fbpp = (len == (uint32_t)w * h) ? 1 : 2;
```

`len == w*h` → RGB332；`len == w*h*2` → RGB565。上位机换色彩模式时**不用改协议、不用重烧固件**。这个设计让后来加 8 位色的改动对固件完全透明。

## 4. 第四步：应用层

`main.c` 里只有三件事：

```c
ST7789_Init();
OrientationTest();          /* 方向卡：红条在上+上箭头，4 秒 */
ST7789_Clear(BLACK);
Video_WaitForStream(0xFFFFFFFF);   /* 死等，直到看见 55 AA */
Video_Loop();                      /* 永不返回 */
```

**方向卡不是装饰**，它是调试工具。四边四色 + 上下箭头，一眼就能判断：

- 红条在上、箭头朝上 → MADCTL (`0x36`) 正确
- 上下颠倒 → `0x36` 参数 `0x00` 改 `0xC0`
- 左右镜像 → 试 `0x60` / `0xA0`

先点亮方向卡，再谈视频。**顺序反了会浪费一整天。**

## 5. 第五步：上位机适配

### 5.1 取帧 → 裁切

```python
# 默认 cover：等比缩放到"盖满"目标方框，再居中裁切，画面不变形
s = max(w / vw, h / vh)
rs = cv2.resize(bgr, (int(vw*s), int(vh*s)), interpolation=cv2.INTER_AREA)
small = rs[y0:y0+h, x0:x0+w]
```

用 `INTER_AREA` 而不是 `INTER_LINEAR`：缩小场景下 AREA 相当于区域平均，抗锯齿，且更快。

### 5.2 量化（8 位色为什么不脏）

直接 `>> 5` 截断会让渐变色出现明显色阶。这里用 **Bayer 4×4 有序抖动**：

```python
_BAYER4 = [[0,8,2,10],[12,4,14,6],[3,11,1,9],[15,7,13,5]]

r = clip((R + t*2 - 15) >> 5, 0, 7)     # 5bit → 3bit
g = clip((G + t*2 - 15) >> 5, 0, 7)
b = clip((B + t*4 - 30) >> 6, 0, 3)     # 5bit → 2bit（蓝色肉眼不敏感，多抖一点）
v[rgb.max(axis=2) < 20] = 0             # 暗部压黑，去掉黑底白噪点
```

几点经验（都是试出来的）：

- 蓝色通道抖动幅度要**加倍**，否则暗部偏紫
- 抖动阈值随亮度衰减，暗部只抖 1/4，否则黑背景全是白点
- 最亮通道 < 20 的像素直接压成纯黑，白噪点立刻消失
- 先做"全额抖动"再加"暗部压黑"，观感比"减半抖动"好

### 5.3 打包与流控

```python
pkt = MAGIC + struct.pack("<HHI", w, h, len) + data + struct.pack("<H", sum(data) & 0xFFFF)
```

ACK 模式：发一帧 → 等 ACK → 再发下一帧，最多重发 4 次；连续 3 帧超时自动降级单向模式。
单向模式：固定节拍 `max(帧长×10/波特率, 0.06) + 5ms`——**这个 0.06 下限很重要**，它对齐了固件刷一帧的时间，不然会越堆越延迟。

### 5.4 打包成 exe

```bash
pyinstaller --noconfirm --clean --onefile --noconsole --name ST7789VideoSender video_sender_gui.py
```

`--onefile` 每次启动要解压到临时目录，70 MB 大约 2~3 秒，正常现象。

## 6. 移植矩阵

### 6.1 换 MCU

| 目标 | SPI1 引脚 | SPI 时钟 | 可跑分频 | UART RX DMA | 注意 |
|---|---|---|---|---|---|
| STM32F103C8 | PA5/PA7 (AF PP) | APB2 72 MHz | /8=9M, /4=18M | DMA1 Ch5 | **20 KB RAM 不够**，见 §7 |
| STM32F103ZE | 同上 | 72 MHz | /4=18M | DMA1 Ch5 | 64 KB RAM，可跑 80px |
| STM32F411 | 同上 (AF5) | APB2 100 MHz | /4=25M | DMA2 Stream0/2 | 128 KB，等同 F407 |
| STM32G431 | 同上 (AF5) | 170 MHz | /4=42.5M | DMAMUX 任意通道 | 32 KB RAM，建议 80px |
| STM32H743 | 同上 (AF5) | SPI123 时钟 100 MHz | /4=25M 起 | BDMA/DMA1/2 | 1 MB RAM，可开三缓冲 |
| ESP32 | GPIO 矩阵任意 | 80 MHz | 可到 40M | 驱动层不同 | 建议直接用 ESP-IDF 的 SPI master + 双核 |

**换 MCU 只做三件事**：

1. CubeMX 里按上面重配 SPI1 + USART1 + DMA，**Mode 3 不许动**
2. 确认 `st7789_hspi.h` 里 `ST7789_HSPI_HANDLE` 指向你的 handle（`hspi1` / `hspi2`）
3. 如果 DMA 通道号变了，CubeMX 会自己生成 `HAL_UART_MspInit`，不用手改

**SPI 提速的安全边界**：ST7789 数据手册写的是写周期最小 66 ns（≈15 MHz），但实际量产屏普遍能跑到 40~60 MHz。提频的步骤是 18 → 25 → 36 MHz 逐级试，每级跑 10 分钟以上看有没有偶发花屏。**花屏往往不是立刻出现，而是温度上来或线长了以后才出现。**

### 6.2 换屏

#### ST7735（128×160，0.96"/1.44"）

改动点：

```c
#define ST7789_W  128
#define ST7789_H  160
#define ST7789_X_OFFSET  0    /* 常见 0 / 2 */
#define ST7789_Y_OFFSET  0    /* 常见 1 / 24 / 0，按现象试 */
```

初始化序列不能照抄（ST7735 需要帧率控制 `0xB1`、`0xB2`、`0xB3` 和电源 `0xC0`~`0xC4`）：

```c
WriteCmd(0x01); Delay(120);           /* SWRESET */
WriteCmd(0x11); Delay(120);           /* SLPOUT */
WriteCmd(0xB1); Data(0x01); Data(0x2C); Data(0x2D);   /* FRMCTR1 */
WriteCmd(0x3A); Data(0x05);           /* COLMOD: 16bit */
WriteCmd(0x36); Data(0xC0);           /* MADCTL: MX|MY，翻转 180° */
WriteCmd(0x21);                       /* INVON */
WriteCmd(0x13);                       /* NORON */
WriteCmd(0x29); Delay(100);           /* DISPON */
```

MADCTL 的四个方向组合：`0x00` / `0xC0` / `0x60` / `0xA0`，逐个试，配合方向卡判断。

**注意**：128×160 是长方形，上位机要发 `W≠H` 的帧。当前固件假设正方形（`ST7789_ShowImageAuto` 里 `240/w` 和 `240/h` 取小），需要改成按目标宽高各自算缩放：

```c
uint8_t s = min(ST7789_W / w, ST7789_H / h);
```

#### ILI9341（240×320）

```c
#define ST7789_W  240
#define ST7789_H  320
#define ST7789_X_OFFSET 0
#define ST7789_Y_OFFSET 0      /* ILI9341 满屏，不需要偏置 */
```

初始化序列更长（电源 `0xCF/0xED/0xE8/0xCB/0xF7`、`0x36=0x48`、`0xB6`、`0xC0/0xC1`、`0xC5/0xC7`、gamma `0xE0/0xE1`），建议直接抄 ST 官方 BSP 或 Adafruit 的 ILI9341 初始化表，**只替换本驱动的 `WriteCmd/WriteData` 调用**。

代价：一帧 240×320×2 = 153 600 B，18 MHz 下 68 ms → **14.6 fps 上限**。想要 30 fps 得把 SPI 提到 36 MHz 以上。

#### GC9A01（240×240 圆形）

分辨率、offset（0,0）、`SetWindow` 逻辑全部照旧，**只换初始化序列**。GC9A01 的初始化非常长且有魔法数，直接抄现成的：

```c
WriteCmd(0xEB); Data(0x14);
WriteCmd(0x84); Data(0x40);
WriteCmd(0x85); Data(0xFF);
WriteCmd(0x86); Data(0xFF);
WriteCmd(0x87); Data(0xFF);
WriteCmd(0x8E); Data(0xFF);
WriteCmd(0x8F); Data(0xFF);
/* ... 约 40 条，见厂商 demos ... */
```

**加分项**：圆屏四角看不见，上位机加圆形遮罩后每帧能省 21.5% 的数据（`π/4 ≈ 0.785`），帧率直接涨 27%。做法是把四角像素置黑再压缩——但协议是定长的，省不了传输量，只能省"视觉噪点"。真要省流量得改协议支持 RLE，不划算。

#### SSD1306（128×64 单色 OLED）

**不建议沿用本协议。** 它是 1bpp + 页寻址（8 行一字节），帧结构完全不同。协议层要重写成 1bpp 位图，`ShowImageScale` 换成取阈值 + 位打包。这条路上，直接找现成的 U8g2 视频播放例子更快。

### 6.3 换传输

#### UART → USB CDC（虚拟串口）

**收益**：全速 12 Mbps，实测吞吐 700 KB/s ~ 1 MB/s，比 1.5 Mbps 快 5 倍以上。80px/8bit 可以打到 100 fps+，瓶颈变回刷屏的 19.5 fps → **直接顶到帧率天花板**。

**代价**：接收模型完全不同，这是移植的真正难点。

| 项 | UART + DMA | USB CDC |
|---|---|---|
| 接收单位 | 一次可以收 28 800 B | 每包最多 **64 B** |
| 完成通知 | DMA 传输完成中断 | `CDC_Receive_FS()` 回调，一次一包 |
| 定长接收 | `HAL_UART_Receive_DMA(p, len)` | 没有这个概念，要自己攒 |
| 超时 | 自己计时 | 靠"多久没来新包"判断 |

改法（**必须改协议层**）：

1. 加一个 64 KB 环形缓冲，`CDC_Receive_FS` 里 `memcpy` 进环，更新 `write_idx`
2. 把 `V_DmaRxStart/V_DmaRxWait` 换成"从环里取 N 字节，够不够 / 超时没有"
3. 帧校验逻辑**一行不用改**（还是按 W/H/LEN 取整帧）

```c
/* 新的接收原语：从环形缓冲取 len 字节 */
static bool V_RingTake(uint8_t *dst, uint32_t len, uint32_t timeoutMs)
{
    uint32_t t0 = HAL_GetTick();
    while (1) {
        if (Ring_Available() >= len) { Ring_Read(dst, len); return true; }
        if (HAL_GetTick() - t0 > timeoutMs) return false;
        /* CDC_Transmit_FS 不忙时，顺手把上一条 ACK 发出去 */
    }
}
```

**坑**：USB 枚举期间（插入后 1~2 秒）主机会发一堆控制包，别在这时候开始收视频；上位机打开端口后 `time.sleep(1.5)` 就是干这个的。

#### UART → SD 卡本地播放（终极方案）

**这是最推荐的"产品化"路线**：不接电脑，插卡就播。

1. 上位机离线把视频转成定长帧序列：

```
video.bin:
  [0x00] Magic "S7V1"
  [0x04] W:u16, H:u16, bpp:u8, fps:u8
  [0x08] frame_count:u32
  [0x0C] frame_size:u32          /* 定长，便于直接 seek */
  [0x10] 帧数据 × frame_count
```

2. 固件用 FATFS 打开文件，`f_lseek(0x10 + n*frame_size)` 定位，`f_read` 读进缓冲，`ShowImageAuto` 刷屏
3. 如果用 SDIO 4-bit，读速 10 MB/s+，瓶颈完全回到刷屏
4. 帧率固定 19 fps 左右；要更快就得用 RGB 并口屏 / FSMC / LTDC

**为什么推荐**：去掉电脑这个不稳定因素，成品感立刻有了；而且帧率恒定，不会因为 USB 掉线卡住。

#### UART → 第二块 MCU / 树莓派

协议不用改，波特率提到 6~12 Mbps（需 SPI/I2C 或高速 UART），或者干脆让上位机用 SPI 从机模式推。**价值不大**，除非要做多屏拼接。

### 6.4 改分辨率 / 改非正方形

| 改动 | 位置 | 说明 |
|---|---|---|
| 支持更大源分辨率 | `video_player.h` 的 `VIDEO_MAX_W/H` | 双缓冲 RAM 按 `W*H*2` 增长，注意总量 |
| 支持非正方形 | `ST7789_ShowImageAuto` | `s = min(W/w, H/h)`，再分别算 `x0/y0` 居中 |
| 支持浮点缩放 | `ShowImageScale` | 不推荐，改成"最近邻 + 双线性只在 1.5× 以下用"更实际 |
| 加圆形遮罩 | `ShowImageScale` 内 | 判断 `(x-120)² + (y-120)² > 120²` 则输出黑 |

**放大倍数与 `s_lineBuf` 的硬约束**：`dw = w * scale ≤ 240`。如果想把源分辨率提到 160，就必须把 `s_lineBuf` 扩到 `240*2`（还是 480 B，不冲突）——真正冲突的是 `VIDEO_MAX_W*VIDEO_MAX_H*2*2` 的 RAM。

## 7. RAM 预算与降级方案

### 7.1 当前占用（F407，144 MHz 编译）

| 项 | 大小 | 说明 |
|---|---|---|
| `s_bufA` + `s_bufB` | 57 600 B | 双缓冲，120×120×2×2 |
| `s_lineBuf` | 480 B | 一整行 240 像素 |
| `s_circleRow` | 162 B | 画圆行缓冲（方向卡用） |
| HAL + 全局变量 + 栈 | ≈ 6~8 KB | 栈设 2 KB 足够 |
| **合计 .bss + 栈** | **≈ 65 KB** | |

F407VET6 有 128 KB（112 KB SRAM1 + 16 KB CCM），余量充足。

### 7.2 小 RAM MCU 的降级路线

按"效果损失从小到大"排列：

| 方案 | RAM | 代价 | 适用 |
|---|---|---|---|
| **A. 降分辨率到 80×80** | 双缓冲 2×6400×2 = 25.6 KB | 画质降，帧率不变（仍 17 fps） | 20~32 KB MCU |
| **B. 单缓冲 + 边收边显** | 单缓冲 12.8 KB（80px/16bit） | 帧率掉到 ~9 fps（收显串行） | 20 KB MCU |
| **C. 只用 8 位色 + 80px + 单缓冲** | 6400 B | 帧率 ~14 fps，色彩差 | 10~20 KB MCU |
| **D. 行级流水** | 480 B 行缓冲 ×2 | 实现复杂，但 RAM 极省 | < 10 KB MCU |

方案 A 只需改两个宏：

```c
#define VIDEO_MAX_W  80
#define VIDEO_MAX_H  80
```

同时把上位机默认 `--size 80`，两边就都对上了。

**判断标准**：编译后看 `.map` 文件的 `.bss` + `.data` + Stack + Heap 总和，留 20% 余量。RAM 不够的症状不是编译报错，是**上电就 HardFault 或画面随机花屏**——因为栈被挤到了缓冲区里。

## 9. 验证方法：分层点亮，别一步到位

移植最容易犯的错是"全部接好、一次烧录、什么都不亮、不知道哪层错了"。正确顺序：

| 步骤 | 做什么 | 验收标准 | 工具 |
|---|---|---|---|
| 1 | 只配 SPI，循环发 `0x01` | 逻辑分析仪看到 PA5 有稳定 18 MHz 方波、PA7 有数据 | 逻辑分析仪 / 示波器 |
| 2 | 加 `ST7789_Init()` + `Clear(RED)` | 整屏纯红 | 肉眼 |
| 3 | 加方向卡 | 红条在上、箭头朝上、四边四色 | 肉眼 |
| 4 | 加 `ShowImageScale` 画固定图案 | 60×60 棋盘格放大 4× 铺满，无错位 | 肉眼 |
| 5 | 加协议层，串口助手手工发一帧 | ACK 灯闪，图案出现 | 串口助手 + Python 脚本 |
| 6 | 接上位机推视频 | 帧率日志稳定，连播 10 分钟不花 | 上位机日志 |

**第 5 步的调试技巧**：写个 20 行的 Python 脚本，只发一帧纯色（比如 60×60 全绿），比一开始就推视频好定位一百倍：

```python
import serial, struct
W = H = 60
data = bytes([0x07] * (W*H))          # RGB332 全绿近似值，随便填
pkt = b"\x55\xAA" + struct.pack("<HHI", W, H, len(data)) + data + struct.pack("<H", sum(data) & 0xFFFF)
serial.Serial("COM3", 1500000).write(pkt)
```

**逻辑分析仪怎么接**：CH0=PA5(SCK)、CH1=PA7(MOSI)、CH2=PA0(CS)、CH3=PA1(DC)。触发条件设 CS 下降沿，解码器选 SPI（CPOL=1, CPHA=2）。一眼就能看出"命令阶段 DC 是不是低"、"每个字节是不是 8 个时钟"。

## 11. 一句话总结

> **别改协议，先点亮屏；别急着推视频，先发一帧纯色；帧率上不去，先算账（串口 vs 刷屏）再动手。**

整套东西里真正有价值的设计只有三个：**SendByte 原语隔离**（让换总线只改 3 行）、**双缓冲 + DMA 重叠**（让吞吐取最大值而不是求和）、**长度自适应位深**（让协议十年不用动）。其余都是调参和试错。
